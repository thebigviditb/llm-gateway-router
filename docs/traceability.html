Task 4 · LLM Gateway

Every requirement, and the code that satisfies it

A traceability guide for the rate-limiting and model-fallback router. Each requirement is quoted from the brief, mapped to the mechanism that meets it, the exact lines, the tests that prove it, and the questions an interviewer is likely to ask.

The 60-second pitch

The gateway sits in front of two model providers. Before it calls anything, it reserves the worst-case token cost of the request in a SQLite ledger inside a write-locked transaction, so concurrent requests can't jointly overshoot the tenant's 50k-per-minute budget. It then calls the primary provider under a hard 3-second deadline. If the primary returns 429, times out, or errors, the router cancels it and calls the secondary. When a response arrives, the reservation is overwritten with the provider's real token usage. If nothing succeeds, the reservation is deleted and the client gets a fixed-shape error with a stable code and a request id, never an upstream message.

Three sentences on why: reserve-then-reconcile is the only way to be exact when output size is unknown up front. asyncio.timeout plus awaited cancellation is what makes the failover race safe. And a single error type with a client-safe message and a log-only detail field is what keeps sanitization from being a per-handler afterthought.

R1

Token-aware sliding-window rate limiter

Implement a token-aware sliding window rate limiter (e.g., maximum 50,000 tokens/minute per tenant API key).

Window and eviction

Mechanism. The ledger is a true sliding log, not fixed buckets. Each admitted request is one row: tenant, timestamp, tokens, state. Usage is the SUM over rows with ts > now − 60. At the start of every reserve for a tenant, rows at or past the boundary are deleted, so the SUM is always over live rows and the table can't grow without bound.

Why a log instead of buckets. Fixed one-minute buckets let a tenant spend 50k at 12:00:59 and another 50k at 12:01:01. A sliding log counts both against each other. The cost is one row per request, which SQLite handles trivially at this scale.

rate_limiter.py:115 _evictrate_limiter.py:127 _retry_after

Retry-After is exact. When a reserve is rejected, the limiter walks the tenant's rows oldest first, summing tokens until the shortfall is covered, and reports when that last row leaves the window. The client gets the earliest guaranteed-safe retry time in both the header and the message.

Proved by test_sliding_window_evicts_exactly_at_boundary, which rejects at 29.999s and admits at 30.000s with a fake clock, and test_retry_after_accumulates_multiple_rows.

Token accounting: reserve, commit, release

The problem. Completion tokens are unknown until the model answers. A single check-then-count is either unsafe (count after, allow overshoot) or inaccurate (count an estimate forever).

The mechanism. Two-phase accounting.

  • reserve(estimate) inserts a row in state reserved holding prompt estimate + max_tokens.
  • commit(actual) overwrites that row with the provider's reported input + output tokens and flips state to committed. Happens microseconds after the response arrives.
  • release() deletes the row when the request produced nothing: both providers failed, or the client disconnected.

The row keeps its admission timestamp through commit, so reconciliation never extends how long the tokens count.

Edge case handled. If a request runs longer than the window, its reservation is evicted like any other row. commit notices the UPDATE hit zero rows and re-inserts the real usage at the current time, so consumed tokens are never lost. test_commit_after_eviction_still_counts_tokens.

Proved by test_commit_reconciles_to_actual_usage (reserve 5000, commit 1234, usage reads 1234), test_release_returns_tokens, and at the HTTP layer test_failed_requests_consume_no_budget.

"What if a response is halfway done and crosses 50k?"

It can't. The reservation already covers max_tokens, so admission is the only decision point. Truncating mid-response isn't graceful and a second model can't continue another model's partial output, so the design moves the whole decision to before the first token.

"Seven concurrent 8k requests, 50k budget?"

Six admit (48k plus small prompt estimates), the seventh gets a 429 before any model is called. Retry-After will say about 60s because it's computed from row expiry, even though the six will reconcile down within seconds. Safe, not tight. A short bounded wait-and-retry in the router would close that gap; I left it out to keep rejection fast.

Concurrency: why two requests can't both squeeze through the last gap

Three layers, each for a different scope:

  • BEGIN IMMEDIATE takes SQLite's write lock at transaction start, not at the first write. Evict, SUM, compare and INSERT are atomic across every connection to the file, including other processes.
  • asyncio.Lock serializes coroutines on the shared aiosqlite connection so two reserves can't interleave statements inside one transaction.
  • WAL mode + busy_timeout make a second process wait up to 5s for the lock instead of getting "database is locked".
rate_limiter.py:146 BEGIN IMMEDIATErate_limiter.py:86 asyncio.Lockrate_limiter.py:91 WAL

Proved by test_concurrent_burst_admits_exactly_the_budget: 40 coroutines each reserving 5000 against 50k; exactly 10 succeed. And test_two_connections_same_file_serialize: 30 reserves split across two independent connections; still exactly 10.

"Why not BEGIN DEFERRED?"

Deferred takes a read lock first and upgrades on write. Two transactions can both read SUM = 45k, both decide 5k fits, and one fails on upgrade with SQLITE_BUSY, or worse, both succeed if the check and write are in different statements. IMMEDIATE makes the read part of the write lock.

R2

Failover on 429 or 3000ms timeout

If the primary model endpoint returns a 429 Too Many Requests status or times out after 3000ms, automatically failover to a secondary backup model provider.

Mechanism. Providers implement one method and may only raise two exception types: ProviderRateLimited for 429 and ProviderError for everything else. The router wraps the primary call in asyncio.timeout(3.0). Three except clauses decide failover:

  • ProviderRateLimited → reason primary_429
  • TimeoutError → reason primary_timeout
  • ProviderError (5xx, connection error, adapter bug) → reason primary_error_*. This is an extension beyond the spec; retrying on another provider is the safe move in every such case.

The secondary runs under its own, longer deadline (10s). If it also fails, the router raises the matching gateway error. It never loops back to the primary.

router.py:106 _call_with_failoverrouter.py:134 asyncio.timeoutproviders.py:127 max_retries=0

The race condition, and why it's closed. The dangerous case is the primary answering at 3.2s while the secondary is already running, and both results reaching the ledger. asyncio.timeout raises CancelledError inside the primary coroutine and does not exit until that cancellation has propagated. So when control reaches the secondary call, the primary can no longer produce a value. Exactly one result exists per request.

SDK retries are off. The Anthropic adapter sets max_retries=0. Otherwise the SDK would silently retry a 429 with backoff, eating the failover signal and stretching the call past the 3s deadline.

Proved by test_primary_429_fails_over, test_primary_timeout_fails_over_and_cancels_primary (asserts the primary saw a cancellation and never completed), test_slow_primary_result_after_deadline_is_discarded (primary set to succeed at 0.1s under a 0.05s deadline; only secondary's tokens are in the ledger), test_primary_within_deadline_wins, and test_both_fail_raises_sanitized_error_and_releases_reservation.

"Why asyncio.timeout rather than the HTTP client's timeout?"

A client-level timeout covers the socket, not the whole call. It can't cancel a coroutine that's stuck between retries or in JSON parsing, and its error type varies per library. asyncio.timeout bounds the entire await and gives one exception type to match on.

"What about the client disconnecting mid-call?"

The handler's task is cancelled. The router catches BaseException, releases the reservation under asyncio.shield so the DB write completes even though the task is dying, then re-raises. test_client_disconnect_releases_reservation.

R3

Standardized error payload, no leakage

Ensure error responses return a standardized gateway error payload without leaking raw upstream stack traces or internal implementation details.

Mechanism. One base class, GatewayError, with two separate text fields: message is client-safe and defaults to a fixed string per subclass; detail is log-only and holds the upstream reason. The wire shape is produced in exactly one function.

{"error": {"code": "UPSTREAM_TIMEOUT",
           "message": "The model providers did not respond in time. Please retry.",
           "request_id": "46afb031bd134ae2"}}

Headers: X-Request-ID always, Retry-After when meaningful. The request id is also in every server log line, so an operator can find the upstream detail that the client was not shown.

errors.py:22 GatewayErrorerrors.py:76 error_responseerrors.py:88–103 handlers

Three handlers cover every path:

  • GatewayError: known outcomes. Logs detail, returns message.
  • RequestValidationError: pydantic failures. Only field names are echoed, never submitted values, so a client can't reflect content back through an error.
  • Exception: anything unexpected. Logs the traceback, returns the generic INTERNAL_ERROR body. Without this, FastAPI's default 500 page is the leak.

Providers also sanitize at the boundary: every SDK exception is converted to ProviderError with the raw text in detail. providers.py:142–148.

R4

SQLite on disk

Use on disk sqlite for database.

Mechanism. aiosqlite over a file path from GATEWAY_DB_PATH. The connection runs in autocommit mode so the limiter issues its own BEGIN IMMEDIATE / COMMIT and controls exactly what's atomic. Schema is one table plus an index on (tenant, ts), which is the access pattern for every query.

Why aiosqlite rather than sqlite3. The stdlib driver blocks the event loop on every call. aiosqlite runs the connection in a worker thread and exposes awaitables, so a slow disk write doesn't stall other requests.

rate_limiter.py:89–94 open()

Pragmas and why:

  • journal_mode=WAL: readers don't block the writer; safe for several uvicorn workers on one file.
  • synchronous=NORMAL: fsync at checkpoint rather than every commit. Durable against process crash; a power loss could lose the last few rows, which for a rate limiter is acceptable.
  • busy_timeout=5000: contention waits rather than errors.

Proved by test_state_survives_reopen (close, reopen, usage intact and limit still enforced) and the two-connection test above.

"Would this scale?"

One writer at a time is SQLite's ceiling, but a reserve is a few microseconds of work under the lock, so thousands per second per node is realistic. Past a single node the same two-phase ledger maps directly onto Redis with a Lua script or Postgres with SELECT FOR UPDATE. The interface wouldn't change.

Trade-offs to volunteer before they ask

Conservative reservation

Reserving max_tokens means a tenant asking for 8k and using 1k briefly holds 8k. Concurrent requests during those few seconds may be rejected when the real numbers would have fit. Mitigations: cap max_tokens per request (already configurable, default 8,192), or reserve prompt + a typical completion size and accept small overshoots. I chose exactness because the brief scores token accuracy.

Retry-After is safe, not tight

Computed from row expiry only, so in a burst it can say 60s when 3s would work. A bounded wait-and-retry inside reserve would fix it at the cost of holding a connection open.

Prompt estimate is chars ÷ 4

Good enough because it's always overwritten by the real count. The exact alternative is the provider's count_tokens endpoint, which adds a round trip per request.

No streaming

Responses are atomic, which is what makes the failover decision clean. Streaming failover after first byte is a different problem: you can end the stream with an error event, but you can't splice in a second model.

Failover on 5xx is beyond the spec

The brief names 429 and timeout. I also fail over on other upstream errors and adapter crashes because the alternative is failing a request that the secondary could have served. Easy to narrow if the reviewer wants strict compliance.
